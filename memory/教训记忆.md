## 构建与验证红线
3. **vite build 绿 ≠ 前端可用**——vite 无 auto-import 时 Rollup 对未解析标识符静默当全局外部名，退出码 0 但运行时 ReferenceError 白屏；前端改动后必须核对 IDE 诊断零错误或 grep dist 特征文案。
4. **静态全绿 ≠ 生效**：AI 面板 segment 修复首轮只改 CSS 变量未加 !important 且没发现文字未渲染，build+grep dist 全过但用户实测"还是一样的"——UI 修复必须 dev server + browseruse 实测断言（computed 值/DOM 文本）。
5. **`wails build -clean` 会清 build/bin/config/ca 换全新 CA**（build.bat clean 的保护对直接调 wails -clean 无效）；增量改 Go 用 `go build -tags desktop,production -trimpath -ldflags "-s -w" -o build\bin\PrismProxy.exe .`。详见环境备忘。
6. **Go 源码中文编码红线**：绝不用 PS `Set-Content`/`-replace|Out-File` 重写含中文源码（默认 GBK 毁 UTF-8，gofmt 报 illegal UTF-8）；改源码一律用编辑工具；手工写 JSON 配置用 `[System.IO.File]::WriteAllText` + `UTF8Encoding($false)`（PS 5.1 `Set-Content -Encoding UTF8` 带 BOM，settings.json 带 BOM 会 json.Unmarshal 失败静默回退 Default）。详见环境备忘。
7. **gofmt 格式**：注释行 `//（` 必须写 `// （`（`//` 后紧跟中文全角括号判格式错）。
8. **go mod tidy 会移除"已声明但未 import"的依赖**——先写 import 再 tidy。

## Go / net-http
9. **net/http server 陷阱（普适）**：POST 带 body 且 handler 未读完时 server 不启动 background read（断连监测），客户端断开后 `r.Context().Done()` 永不触发→httptest handler 挂死→`srv.Close()` 死锁。测试解法：handler 先 `io.Copy(io.Discard, r.Body)` + done channel select 兜底 + 断言后 close(done)。
10. **锁重入死锁红线**（persist）：pmu 临界区内严禁调用同步触发 store emit 的方法（st.Add）——emit 在解锁后同步回调 onPersistEvent 又取 pmu→同 goroutine 二次加锁永久死锁。约定：pmu 只保护 writer 指针；订阅与历史补载一律解锁后执行。锁序铁律：`projMu → a.mu/a.pmu`，禁止反向。
11. **Wails 绑定方法返回值铁律：最多 2 个且末位为 error**——`internal/binding/boundMethod.go` 的 Call 仅 case 1（单值/error）/case 2（(value,error)），**输出数 ≥3 时无 case 命中，returnValue 与 err 都保持零值 → JS resolve(null)、不报错**，被前端 `?? []` 兜底成空态（真实 Wails v2.15 实测静默返回 null，最初以为会给数组）。多返回值解构目标 `r` 本身可能为 null（空归档库/浏览器 mock 整体 return null），只写 `r[0] ?? []` 会抛 Cannot read properties of null；修法=单结构 DTO 包装绑定 + `r?.x ?? 默认值`。修法实现见后端代码记忆「Wails 绑定规则」。
12. **跨 shell 引用规则差异必须逐字实测**（`\"` 只在 cmd 有效，PS 中直接闭合字符串）；白名单必须以 DevTools 源码 + 用户真实样例双重核对（DevTools main 源码白名单不含 `()`，但 Chrome 152 样例 UA 括号无 `^`，以样例为准）；用户贴回的命令可能被聊天框 markdown 渲染篡改，排查先本地逐字节比对。Git for Windows 精简版无 curl。
12b. **Go http.Transport 复用空闲 CONNECT 隧道时不再回调 `transport.Proxy` 闭包**（2026-09-18 方案1 实测踩中）：首条 HTTPS 流经 Proxy 闭包能拿到上游，rotate 后同 host 的第 2、3 条流因隧道复用闭包不触发→记录的 UpstreamAddr 为空。铁律：**每请求级数据（上游节点/出口 IP 等）必须在调用 RoundTrip 前显式解析并经 `r.Context()` 载体传递，绝不能依赖 Proxy/Dial 闭包回调**。407 轮换重试后也要重新解析回填。
12c. **排查「代理在转发但列表无新流」先分清 MITM vs 盲隧道，别误判成录制器坏了**（2026-09-18）：本机 curl 不带 `-k` 不信任 Prism 假证书→TLS 握手失败→host 进 bypass→重连走盲隧道；盲隧道流 URL 是 `https://<host>:443`（**无 query/path**），用 `--filter "u=唯一串"` 必然查不到，看似「没录」其实已录。验证 MITM 路径 curl 必须加 `-k`；查盲隧道流按 host 过滤看 `URL=https://host:443`、Method=CONNECT 形态。
12d. **请求级 holder 审计三要点**（2026-09-18 方案1 代码审计修正）：①坏点归因必须用本请求权威的 `holder.addr`，不能读 Server 共享的 `curUpstream atomic.Pointer`——并发请求可能已把它改写为别的节点，导致 407 坏点记错/漏记（DialContext 闭包通道仍读 curUpstream，属"只可能漏报不误报"的可接受竞态，注释已标注）。②407 轮换后 `resolveUpstream` 返回 err 时**不能保留旧 holder 重放**（Proxy 闭包会把重试再发回刚判坏的同一节点），应直接透传原 407、不重试；返回 (nil,nil)=降级直连才是正常分支。③holder 要带显式 `resolved bool`：Proxy 闭包若用 `h.ep != nil` 判空，直连（ep=nil）时会误判为"未解析"而二次 resolveUpstream（resolver 模式多一次取货/状态副作用）；以 resolved 判定，只有真正无 holder 的兜底路径才自行 resolve。

## 前端 / Vue / naive-ui
13. **模板内 JS 模板字符串以 `}}` 结尾会与 Vue 插值冲突**——改用拼接/计算属性（AI 面板日志消息全部 script 内拼接）。
14. **多入口 Vite 项目组件样式不得依赖入口级 css，须由共用祖先组件 import 进共享 chunk**（P4 H1 高危：AI 样式全放 review.css 仅独立入口 import，主窗内嵌形态样式全缺；现由 ReviewPage.vue import ai.css 单点覆盖双形态）。
15. **naive-ui 2.40.4 normalizeSlots bug**：`vue-jsx-vapor/vdom.mjs` 的 normalizeSlots 对任何非函数非对象输入（含 undefined）包装成 truthy slot；**自闭合 `<n-tab-pane :tab="..."/>` 的 tab 文字根本不渲染**（DOM 为空 span，capsule 被压成 8px"进度条"）；带子内容的 n-tab-pane 不受影响。纯导航 tab 改用 `n-tab`（label 走 default slot）。
16. **naive-ui 把主题变量以内联 style 挂组件根**（`--n-color-segment` 等），普通 CSS 规则盖不过内联，必须 `!important`（样式表 !important > 内联 normal）。
17. **CSS 变量定义位置**：组件样式依赖的变量必须定义在组件自己的 css 内（如 ai.css `:root { --ai-brand }`），不得依赖入口级 css（同 14）。
18. **disabled 按钮的 NTooltip 必须外层 span 接管 trigger**（原生 disabled 不派发鼠标事件）。
19. **Vue scoped 样式与插槽**：父传给子的具名插槽内容在父作用域编译，子 scoped 样式不命中——样式放父组件（pin 图标/历史 badge/标签徽章在 FlowList.vue）。
20. **useVirtualList 空态陷阱**——wrapper 高度随内容收缩，空行 wrapper 高 0，空态必须移出虚拟容器并绝对定位。
21. **live region 须常驻无障碍树**：aria-live 挂 v-if 动态插入的节点读屏无效（display:none/visibility 一样移出无障碍树）；须常驻 sr-only 节点文本随状态切换。
22. **mock 预览验证手段**：浏览器自动化（CDP 注入）产生的合成点击是 `isTrusted=false`，naive-ui NDropdown 选项的 handleClick 不响应（普通按钮/clickoutside 正常）——验证右键菜单业务分支可经组件实例 `el.__vueParentComponent.setupState.onCtxSelect(key)` 直接驱动；真实鼠标点击不受影响。浏览器 mock 下主窗内嵌复盘无 Review* 绑定，console 有「未实现的绑定」warn 属预期；独立 `review.html?token=mock` 走 DemoApi 才有演示数据。
22b. **useVirtualList 数据变短回顶不能靠 nextTick 读 scrollHeight**（2026-09-18 实测）：watch rows.length 若在回调里读 `el.scrollHeight`，拿到的是变更前/未刷新的占位高，越界判定漏过；随后虚拟列表按旧 scrollTop 计算可见区间，区间整体越界 → 渲染 **0 行卡死空白**，且 rows.length 不再变化、watch 不再触发。正确修法：watch 回调用**行数同步换算最大滚动距离**，不读 DOM 高度、不用 nextTick。机制底层（读 vueuse 源码确认，index.cjs L7419 useWatchForSizes 为默认 **pre** watcher）：vueuse 只在显式 scrollTo() 写容器 scrollTop，render patch 仅改 wrapper 的 height/marginTop；我方在 pre 阶段把 scrollTop 置 0 是真实变化 → 浏览器必派发 scroll 事件 → calculateRange 以 0 重算恢复首屏，故不会白屏。现象判据：清空后 `.list-body` scrollTop 停在数千但 `.row.item` 数量为 0。

22d. **虚拟列表「内容总高」只含渲染窗口的边框，未渲染行边框不累积——审计建议也要回源码验**（2026-09-18）：`.item` content-box + `border-bottom:1px`，行数换算若用 `N×(itemHeight+1)`（审计给的修法）是**错的**：vueuse 虚拟列表只渲染约「可视行数 + 2×overscan」行，未渲染的上千行只贡献 wrapper 的 `N×H` 占位高，其边框不进真实 scrollHeight；`N×(H+1)` 会把 maxScroll 高估几百 px，导致清空长列表时**永不触发回顶**（比原 bug 更隐蔽）。正确：边框修正取 `min(N, ceil(clientHeight/H) + 2×overscan)` 有界常数（约几十 px）。教训：①普通流堆叠 ≠ 所有 N 行都真实渲染，盒模型外推前先确认虚拟窗口；②代码审计结论同样要回源码/实测验证，不能照单全收。另：ReviewPage reset 回顶在 `await nextTick()` 后补了 `if (my === flowSeq)` 代际校验，防过期请求把新列表位置归零。

22c. **模板内联「先写 ref 再调带防重入守卫的 handler」反模式**（2026-09-18）：`@click="scope = 'all'; onScopeChange('all')"` 看似稳妥，实际模板里裸 `scope='all'` 已写入 `scope.value`，而 handler 首行是 `if (v === scope.value) return` 的防重入守卫 → 恒相等直接 return，**不发请求、不重拉关联数据**，按钮点了像卡死。铁律：handler 内部本就负责赋值+副作用时，模板只调 handler，不要预判式预写状态。排查判据：点按钮后摘要/分页数字变了但列表共 0 条、network 无新请求。

25. **FlowTable 列 `wi` 不是随意 id，而是「数组下标+1」的硬契约**（2026-09-18 上游列审计高危）：共享表格以 `columns[wi-1]` 反查列定义、`colWidths[wi]/colMins[wi]` 取宽、拖宽/右键菜单按表头 class 的 `findIndex(...)+1` 定位。在 columns 数组【中间】插一列时若给个大编号（upstream wi=10 而它在数组下标 8、tags 仍 wi=9），会导致：默认视觉两列内容对调（wi=10 槽渲染 columns[9]=标签）、宽度对调（colWidths[10]=110 用到标签槽）、右键/拖宽操作错列；且能通过 applyLayout 全部校验（长度合法），问题极隐蔽，build/vet 全绿也发现不了。铁律：**wi 必须随数组位置连续升序，中间插列必须对后续列做身份重编号；列布局迁移里 widths 按 wi 下标搬运（不是按 colOrder 位置切片），并单独处理「被隐藏列 order 不含旧 wi、但 widths 数组仍占槽」的边角。** ReviewPage 在数组末尾追加列天然连续，可作正确范本。另：开发期写过错的新版 layout-key 会残留在 `%APPDATA%\PrismProxy.exe\EBWebView\...\Local Storage\leveldb`，启动优先生效，未发布版本验证前应删 leveldb。

## browseruse / 前端自动化验证
23. **browser_evaluate IIFE 陷阱**：script 用 `(() => {...})()` 包裹会被引擎二次包装返回 undefined（skill 有明文警告），多语句也返回 undefined；**解法=逗号单表达式** `(v1 = x, v2 = y, ..., JSON.stringify({...}))` 配隐式全局变量。
24. **Vue 响应式 DOM 更新是异步微任务**——browser_evaluate 里同步 dispatchEvent 后立刻读 DOM 读不到新高度（内联 style 仍 null），必须 wait 1s 后再读；合成 PointerEvent（bubbles+pointerId+pointerType:mouse）驱动 window 级监听完整可行。dblclick 后 0ms 立即拖拽会撞 height transition（起始 rect 仍旧值），测试时需 wait。

## AI / Ollama 外部产品行为（影响设计）
25. **批量 prompt 尺寸红线**：intent 单批打包 prompt 正比于流数，9 条≈5.5KB（安全）、27 条≈16KB 在 Ollama 上首响应超时被判死；稳妥批量策略=**≤10 条/批**。
26. **Ollama 运行时 ctx 预算 ≈8K tokens**（远小于模型标称 262144，那是模型上限非运行时值）——input+思考+输出超预算 → finish=length 静默截断、content=0，大批量必踩；**只能 Modelfile `PARAMETER num_ctx N`（或服务端 OLLAMA_CONTEXT_LENGTH）扩窗 + 拆批规避——经 /v1/chat/completions 请求体发 options.num_ctx 会被静默忽略（HTTP 200），见教训 33**。
27. **/no_think 软开关对 qwen3.5:4b 实证不可靠**（system 末尾/user 末尾双注入仍出 11–14K 字符思考）——唯一可靠解=Ollama 原生 `/api/chat` 的 `think:false` 硬开关（shim 方案）。
28. **Ollama 对不存在模型秒回 404 error.message（非超时）**；超时≈模型名有效但 prefill 慢（本地模型冷启动/长文本推理慢，自托管首块超时取 Timeout 全额）。
29. **测试连接小 prompt 探不出首块超时差异**（TTFB≈0.2s），批量长 prompt 才暴露——性能问题要用真实尺寸负载测。
30. **「卡死」先证伪再修**：续写卡状态条实测并非死锁，而是三层叠加（思考增量被丢弃无进度反馈/思考吃光输出预算/首块后无帧间看门狗）+ 上游 8K ctx 截断。手法=PowerShell curl.exe 直打 SSE `-o` 落盘再解析各 delta 时间戳与 reasoning/content 字符数（HttpClient ReadLine 曾产生 137MB 空引用输出，弃用）。PS 坑：写 JSON body 必须 `UTF8Encoding($false)`，BOM 致 Ollama 报 `invalid character 'ï'`；字符串内插值在数组/哈希场景用 `${var}` 不用 `$(...)`。
31. **thinking 模型不适合做压缩/续写工具调用**（qwen3.5:4b 实测：压缩 81s、前 70s 只吐 reasoning；续写正文仅 1202 字符 vs reasoning 13.7K，且极易再 length）。环境调优顺序：①压缩/续写工具调用换非思考模型（如 qwen2.5:7b-instruct）；②扩上下文走 Modelfile `PARAMETER num_ctx 16384+`（请求级 num_ctx 在 /v1 无效，见 33；或服务端 OLLAMA_CONTEXT_LENGTH）；③批量 ≤10 条/64KB 按预算拆；④占位 apiKey（如 "123"）会被 `APIKey==""` 自托管判定为假→首块/空闲阈值按云端 30s 收紧，本地 Ollama 条目 key 应留空。
32. **新增 AI 配置字段必查 SaveSettings 白名单**：bindings_settings.go 的 `g.AI = settings.AIConfig{...}` 是逐字段白名单拷贝，只改 settings 结构体+投影+bridge 而漏白名单，设置页保存静默丢字段（NumCtx 审计中曾抓出此漏，后该字段整体回退）。检查清单：settings 结构体+AISettings 投影+Validate → SaveSettings 白名单 → ai_bridge PATCH case+aiConfigView+Client 装配 → wailsjs models.ts 双类 → 前端 types/wails.ts/mocks/默认值。
33. **OpenAI 兼容 ≠ 原生 API：第三方特有参数不要假设能经 /v1 透传，必须实证**。2026-09-12 凭「Ollama 文档说兼容 OpenAI」实现了 settings num_ctx→`options.num_ctx`（/v1/chat/completions）全链路并写进记忆，代码审计才发现 Ollama 兼容层 ChatCompletionRequest 根本无 Options 字段，ShouldBindJSON 静默丢弃、HTTP 200 无任何信号；官方文档明说 OpenAI API 无法设置 context size。现场 needle 探针三重证实（/v1 带 num_ctx:256 仍完整保留 3037 token 且回忆出开头暗号；/api/chat 对照组正确截断到 1024、暗号丢失）。**静默接受+假装生效是最坏失败模式**（用户以为扩了窗，长抓包依旧被截）。修法：对供应商特有能力先查其兼容层请求结构体/官方兼容文档，并用「故意小值+needle 在开头」探针实测；能控上下文的正道=Modelfile PARAMETER 或原生 /api/chat（本项目恒走 /v1，双协议未做，故选引导文案）。
34. **空态/可用性判定前后端口径必须同源，不能前端另起一套**。2026-09-12 用户报 Ollama 空 key 被复盘页挡「未配置 API Key」：后端 `WarnNoKey()` 早已豁免 provider=ollama、AiTab 也有同口径，但 ReviewAiPanel 的 cfgOk/showEmpty 只看掩码视图的 `hasApiKey` 布尔，把后端豁免规则漏在前端。修法：前端 keyReady 按 `hasApiKey || provider==='ollama'（顶层 + entries 当前条目双查）` 复刻后端判定。铁律：凡「某供应商免 key/免填」类规则，后端有单一事实源（如 WarnNoKey）时前端应直接消费其结论（keyMissingWarn 为空即就绪）或严格同口径复刻并在注释锚定后端函数；只加供应商预设而不审所有 hasApiKey 消费点，必漏。

### 系统 CA 注入软件化（2026-09-16 第二轮，bindings_adb_cert.go）
38. **Windows adb 跑设备 shell，禁用 `adb shell sh -c "<含 ; && | 多参数的脚本>"`，一律 push 脚本后单参数执行**。Go exec 虽按 argv 独立传参，但 Windows adb→toybox sh 链路会把含分号/空格/管道的 `-c` 串二次拆分：实测 `sh -c "ls /x 2>&1; echo rc=$?"` 退化成「列根目录 + rc=0」、`if [ ... ]; then ... fi` 报 `syntax error: unexpected then`、`readlink a; readlink b` 报 `Needs 1 argument`。**坑在探针静默返回错误结果而非报错**（test -f 对不存在文件返回 NO 看起来很正常），一度误判成「挂载传播延迟/命名空间竞态」绕了很久。铁律：设备侧任何超过单条简单命令的逻辑，写成 `#!/system/bin/sh` 脚本 `adb push` 到 `/data/local/tmp/`（设备无 /tmp），再 `adb shell sh /data/local/tmp/x.sh <参数>`；判断结论用唯一标记串（PRISM_CERT_OK/INSTALLED/MISSING）回显，不靠退出码（toybox su 透传不稳定）。
39. **雷电同机双 transport：`adb devices` 同时列 `emulator-5554` 和 `127.0.0.1:5555`，空 serial 一律 `more than one device/emulator`**。这是同一台设备的两个入口（设备号、状态完全一致），不是两台设备。空 serial 是 UI 默认值（用户通常不填），必须后端自动选：`resolveSerial` 见 emulator-* 即优先它（去重其网络回环），仅在真有多台不同物理设备时才要求填序列号。**注意自动注入曾因此在 best-effort 里静默失败**（push 报 more than one device 被 runtimeLogf 吞），现象=代理 set 看似成功（实为设备 /data 里 http_proxy 重启后持久化的假象，连 set 本身当时都失败了）但证书没注入。
40. **诊断 adb 问题时命令本身也要带 `-s <serial>`**：本轮手工 `adb reboot`（无 -s）在双 transport 下直接 `more than one device` 失败，却没第一时间注意，以为设备已重启、对着旧状态（证书仍 INSTALLED）排查了一轮。铁律：这台环境里任何 adb 实操命令都显式 `-s emulator-5554`，并用 `getprop sys.boot_completed` + 独立探针脚本确认重启真的生效后再下结论。另：`adb root`/reboot 会重启 adbd，期间 `wait-for-device` 命令在双 transport + GUI 同时占用 adb 时可能长时间静默挂起，必要时 StopCommand 后换新终端查状态。

## 代理池真账号联调（P5，2026-09-17）
41. **厂商枚举值域必须锚定官方文档原文，禁止凭印象写映射**：ProxyPoolSection.vue 的 ispOptions 写成 `2=联通 3=移动`，91HTTP 官方文档实为 `1=电信 2=移动 3=联通`——用户选「联通」实际发 isp=2 拿到移动 IP，mock/单测全部发现不了（前后端契约自洽但与厂商真实语义脱节），真账号联调核对官方文档才暴露。修法：修正映射并在注释锚定「值域与 91HTTP 官方一致」。铁律：凡透传给厂商 API 的枚举值，一律在注释里写官方来源并对照原文。
42. **CLI usage 文案也是契约，改实现必须逐字核对**：usage 写 `--secret-file - 从 stdin 读取`，实现是 `--secret -`（设计 §8.3 G8 本意如此），用户照 usage 敲命令直接报「读取密钥文件失败」。单测只测实现路径，测不到文案。修法：usage 改与实现一致；铁律：CLI 帮助段变更或新命令入册时，把 usage 里每个 flag 当 API 契约核对一次。
43. **PrismProxy 的 exe 必须 `wails build`，裸 `go build` 只供 headless/测试**：用 `go build -o build/bin/PrismProxy.exe .` 覆盖了 wails 产物后，双击启动弹「Error」窗口随即静默退出（exit 0、无任何 Go 日志）——根因是裸 go build 不生成 `.syso`、`build/windows/wails.exe.manifest` 未链接进 exe，WebView2 初始化失败由 wails 弹原生对话框；headless 不启动 WebView2 故表现正常，极具迷惑性。修法：`wails build` 重建即恢复。铁律：给用户用的 exe 一律 `wails build`；排查「GUI 无声退出 exit 0」先怀疑 manifest/WebView2 而非 Go 代码。附带确认：`wails build` 重新生成 bindings 与 P3 手动同步的 wailsjs 零漂移。
44. **哨兵字段的所有消费路径都要做合并，不能只覆盖保存路径**：secret/password「空串=保持」哨兵只在 ProxyPoolSaveProvider 做了合并，ProxyPoolTestFetch 纯入参直传厂商——用户保存密钥后重新打开编辑框（secret 框按设计置空）点「测试提取」，空 secret 直传 91http 报「secret不得为空」，现象=「明明填了密钥还说为空」。修法：TestFetch 按 id 寻址已存账号做空串合并（含 tradeNo），`__clear__` 按空不透传。铁律：新增哨兵语义时，列出该字段的全部出入口（保存/测试/预览/导出），逐条确认空值含义一致；厂商报错文案（如「不得为空」）也是定位线索，先分清是本地校验还是上游透传。
45. **注入给子组件的回调若内部要取外部锁，绝不能在外部持锁栈上同步执行——状态通知一律走队列/异步**（2026-09-17 P5 真账号首启 pool 时踩到，现象=点「启动代理并提取 IP」永久转圈、整个 ctl API 9595 超时）。死锁链：`startProxySnap` 持 App.mu → `ensureProxyManagerLocked` → `mgr.Start()` → `kickFetch()` 在同栈同步调 `onChange(st)` → 回调 `onPoolStatus` 第一行 `a.mu.Lock()` → goroutine 自锁，App.mu 永不释放。原代码注释虽写「onChange 锁外调用」，但只是 Manager.mu 外、仍在调用方（App.mu）锁栈里，B1 只管「网络 I/O」没管「回调重入」。修法：Manager 加 notify chan(64) + 单消费者 dispatcher goroutine，5 处状态通知全部 `notifyLocked` 投递，回调只在 dispatcher 执行（串行保序，缓冲满丢中间帧）；回归测试 `TestManagerCallbackNoCallerLockReentry` 持外部锁 Start 验证不死锁。铁律：跨层注入的回调，默认当作「会反向拿你的锁」，持锁路径上只能投递信号（channel/atomic），不能同步调用；写注释说「锁外调用」必须指明是哪把锁。
46. **「每轮新建的信号通道」所有权必须随创建者走，Stop 幂等**：同轮修复中测试暴露 `close of closed channel`——旧 Stop 先把 fetching=false 再 wg.Wait，停机竞态下 run 循环可再 kickFetch 重建 inflight，旧 fetchOnce 收尾 close 掉新一轮通道。修法：kickFetch 建 `ch` 传给 `fetchOnce(ch)`，收尾仅当 `m.inflight==ch`（我仍是当前轮）才 fetching=false+close；Stop 先置 stopped 占位、尽力投递停机帧（notifyStoppedLocked 与 ctx.Done 二选一）、cancel、wg.Wait（不 close notify、不 wait dispatcher——见教训 50），且 stopped 已置时直接返回（幂等，测试 helper 的 t.Cleanup 与显式 Stop 双调安全）。铁律：channel close 权归创建者，跨协程复用时用指针相等判定归属；Stop/Close 类生命周期方法默认要幂等。
47. **锁内「条件分支 Unlock+return、函数末尾再 Lock 同一把锁」的写法必须在每个 fall-through 分支显式 Unlock**（2026-09-17 审计修复 M2 时自引入，go test 全量 10 分钟超时抓出）。resolve 新增「第二个 promoteLocked 块」只在命中分支 `m.mu.Unlock(); return`，未命中直接掉到下方 `m.mu.Lock()`（OnEmpty 块）= 不可重入自锁；Go 互斥锁自锁不是编译错误也不立即 panic，表现为该路径永久挂起（池空首次解析必现）。修法：未命中分支补 `m.mu.Unlock()` 再重新加锁。铁律：同一函数内分段取同一把锁时，优先改成单锁区段；必须分段则逐分支核对配对，并依赖「池空/OnEmpty 路径」的回归测试兜底（本次正是 TestManagerOnEmptyError 抓到）。
48. **外部错误的 Error() 文本可能含敏感参数，入 lastErr/日志前必须脱敏**（审计 M1）：Go 传输层错误是 `*url.Error`，其 Error() 直接拼完整 URL，`http://host/path?secret=xxx&trade_no=yyy` 会随 Fetch 错误进 Manager.lastErr → PoolStatus DTO → SSE/Wails 事件/CLI stdout/日志，网络一抖就泄密（91http 铁律 3「只记 path」被错误分支绕过）。修法：errors.As 取 *url.Error，url.Parse 后只保留 Op+Path+底层 Err（sanitizeURLError），回归测试断言错误串不含 secret/trade_no 值且保留路径。铁律：凡把 err.Error() 透传到对外 DTO/日志的边界，先确认该错误类型的字符串组成；HTTP 客户端错误一律视为含 URL。
49. **池运行时「current 空缺」必须先消费备用池再考虑补池/降级**（审计 M2）：旧 resolve 空缺即 kickFetch+等待，备用池有货也可能因等待窗口/退避直接走到 OnEmpty=direct 降级——手里有未过期 IP 却让流量裸奔真 IP，违反代理池核心安全预期。修法：resolve 开头与等待结束后各 promoteLocked 一次。铁律：降级直连是最后手段，其前置判定必须穷尽「手上所有可用条目」（current→备用池→等待新提取），顺序不可跳。
50. **重建同名监听者的对象，旧对象的延迟回调要有代际过滤**（审计 M3）：Manager 重建（改账号）时旧 dispatcher 不被 Stop 等待（其回调反向取 App.mu，等待即死锁，见教训 45），队列滞留的 running:false 停机帧可能在新 Manager 启动后才执行，覆盖新池 running:true。修法：App 持原子 poolCur 作代际基准，闭包内 `poolCur.Load()!=mgr` 的帧丢弃；先 Store 新代再 Stop 旧。铁律：「不停旧协程、只让它自然消亡」的模型必须给回调配代际/epoch 校验。
51. **Wails v2 `EventsOff(name)` 按事件名注销全部监听者，多组件订阅同名事件必须单订阅+引用计数**（审计 M4）：AppFooter 与 ProxyPoolSection 各自 EventsOn('proxypool:status')，任一组件卸载 EventsOff 会把另一个的监听一起杀掉（从设置页回主界面后底栏不再更新）。JS 侧无注销句柄。修法：composables/usePoolStatusEvent.ts 模块级 Set 聚合 handler，EventsOn 只注册一个 dispatch，卸载时最后一个 handler 移除才 EventsOff。铁律：Wails 事件按名共享，封装成单订阅 composable，组件不得直接 EventsOff 共享事件名。
52. **前端跨组件轮询/等待循环必须随组件卸载取消**（审计 L2）：enableAndFetch 的 waitForCurrent 用绝对 deadline 轮询，组件卸载后仍继续 await→set ref→naive-ui 「卸载后更新」告警/无效请求。修法：模块级 alive 标志，循环条件与每次 await 后都判定。铁律：任何带 await 的轮询，alive 检查要同时放在循环条件和 await 之后两处。
53. **双生组件抽共享函数时两份都要接完，且 import 漏写 vite build 照样绿**（2026-09-18 主窗「调试重发」预填报 `expandEditableHeaders is not defined`）：上一轮把预填逻辑抽到 `lib/composer.ts` 只改了 review/components/ReviewComposer.vue，主窗 pages/Composer.vue 里调用点换成了共享函数名却漏 import（本地还残留一份死 HOP_HEADERS）；`<script setup>` 未解析标识符被 Rollup 当全局外部名（同教训 3），build 0 退出码、IDE Vue 诊断有时也不刷，直到点按钮 watcher 执行才 ReferenceError（被 try/catch 包成「预填请求失败」提示）。修法：补 import、删死常量。铁律：①主窗 Composer 与 ReviewComposer 是双生拷贝，共享逻辑改动必须 grep 两个调用点逐一核对；②疑似未定义引用直接全局 grep 标识符的 import/定义，别信单文件 build。

54. **CLI 帮助请求必须走 stdout + exit 0，凡文档写明的调用形态都要在 stdout-only 捕获环境实测**（2026-09-19）：用户报「cli help 没有输出」，实测 `cli help` 正常（stdout/exit 0），真因是文档（AI-CLI使用说明.md §441）推荐的 `cli --help` 形态把 usage 只打到 stderr 且 exit 2——flag 包遇未定义 `--help` 走 ErrHelp 按 fs.Output()（stderr）打一遍 usage，随后「无子命令」兜底又打一遍（共两遍）；仅捕获 stdout 的调用方（AI 工具/重定向/CI）看到的就是空输出。修法：RunCLI 里 `fs.Usage = func(){}` 禁用解析期自动输出，Parse 返回 `flag.ErrHelp` 时 `printCLIUsage(os.Stdout)` + return 0（`-h` 同效）；解析错误/无子命令仍 stderr + exit 2（flag 包错误行已自带，usage 单遍不再重复）。铁律：帮助是正常请求不是错误；CLI 输出分流后，用户会敲的每种调用形态都要验证「stdout 里有什么、退出码是什么」。

55. **wails windowsgui exe 从 cmd 直接启动时无标准句柄且未附着控制台，全部 CLI 输出静默消失**（2026-09-19，PRISM_CLI_DEBUG=1 实测）：GUI 子系统进程被 cmd/PowerShell 直接启动时 `GetStdHandle` 返回 **NULL**（不是「继承来的无效句柄」——v1 的「句柄非空即可用」判断因此失效），且进程完全未附着控制台（GetConsoleWindow=0、GetConsoleProcessList=0），os.Stdout 写入凭空丢失；而 PowerShell/重定向/AI 工具（经管道启动）句柄是可写管道。修法（main_windows.go `attachParentConsole()`，main_other.go 空实现，CLI 入口先调用）：①对 out/err 句柄做 **0 字节 WriteFile 探针**（管道/文件成功，NULL 失败），全可用直接返回；②探针失败则 `CreateFile("CONOUT$")` + GetConsoleMode 验证后重接 os.Stdout/os.Stderr（CONIN$→os.Stdin）；③CONOUT$ 打不开（未附着控制台）再 `FreeConsole()+AttachConsole(ATTACH_PARENT_PROCESS)` 后重试②。诊断：`PRISM_CLI_DEBUG=1` 时全过程追加写 `%TEMP%\prism_cli_attach.log`。已知边界：trae AI 终端沙箱内 AttachConsole 恒报 Access denied（ConPTY/conhost 承载均复现），附着路径只能在真实桌面 cmd 验证；正常桌面会话 Free+Attach 是 git/chrome 同款标准做法。附着力坑（同日第四轮实测）：①cmd/PowerShell 打提示符后**不等待 GUI 子进程**，接通输出后首行会与提示符拼在同一行（`D:\...>PrismProxy cli — 控制…`，用户误以为命令被执行两次）——附着路径输出前必须先 `Fprintln(os.Stdout)` 换行（只在 `!outOK` 分支，管道场景不加）；②测 GUI exe 管道行为勿用 PowerShell `$o = & exe`（不等待 + 捕获竞态读空、$LASTEXITCODE 为空），用 `Start-Process -Wait -PassThru -RedirectStandardOutput` 或 cmd 重定向到文件再读。**进程内无解的最终界限（第五轮）**：换行只治「同行拼接」，治不了「输出落在下一个提示符之后」——cmd/PS 对 windowsgui 进程发射后不管，输出次序由 shell 决定，GUI exe 内做什么都没用。终解=**console 子系统独立入口 `prism-cli.exe`**（初名 prism.exe，2026-09-19 按用户要求更名；`go build -tags prismcli -o build/bin/prism-cli.exe .`，console 是 go build 默认无需 -H）：shell 必然等待 console 进程，输出/退出码次序天然正确；prismcli tag 只切 guard（非 cli 参数报错引导 exit 2，guard_gui.go 空实现），usage exe 名按 `filepath.Base(os.Args[0])` 参数化。铁律：①wails GUI exe 内嵌 CLI 时 CLI 入口必须先 attachParentConsole；②判断 std 句柄可用性要用 0 字节写入探针，「句柄非 NULL」不等于「可写」；③「终端里没输出」先分清没打到 stdout 还是进程根本没句柄——用管道启动复测即可区分；④GUI 子系统进程对 shell 是「发射后不管」，交互式终端的正确 CLI 次序只能靠 console 子系统入口保证——给终端用户的 CLI 一律走 prism-cli.exe，附着+换行只是 GUI exe 直跑时的缓解。

56. **锁内校验 + 锁外执行 = TOCTOU 窗口，校验与副作用必须在同一持锁区段完成**（2026-09-19 CLI 显式化方案审计发现）：ctlService.DeleteProject 原设计在持 projMu 内 resolve+校验「目标不是当前项目」，解锁后再调 App.DeleteProject 执行删除——窗口期 GUI 可把目标项目切成当前项目，删除随即触发自动切换，违反「CLI/HTTP 不变更全局当前项目」不变量，且并发测试与普通单测都难复现。修法两要点：①拆 `deleteProjectLocked`（Locked 后缀约定=调用方已持 projMu），桥接层全程持锁完成 resolve→拒删当前→删除；②**Go Mutex 非重入——持锁时绝不能调用会自己取同一把锁的 `App.DeleteProject`，否则永久死锁**（与教训 10/45 同族）。回归检测手法：用 `projGen` 代际是否推进判定「发生了隐藏切换」（TestCtlDeleteProjectRejectsBecameCurrent / TestCtlDeleteProjectConcurrentSwitch）；本机无 64 位 gcc 跑不了 -race，竞态正确性只能靠锁序设计+代际断言兜底。

57. **重编译后必须重启常驻 headless 实例再实测，CLI 实测验证的是「CLI+服务端」两端整体，一端旧版本结果就是旧语义**（2026-09-19 显式化实测踩到）：T9 `project create` 后 `project list` 显示 currentProject 被切到新项目，疑似「create 不切换」未生效；逐层排查 createProjectNoSwitch→settings.CreateProjectDir→NewProjectID 全链路均无 CurrentProject 写入，代码干净。真因：环境残留**两个 PrismProxy 实例**——重编译（14:23:00）前启动的旧实例（11:08）仍占用 ctl 9595 并持有 config\ctl-endpoint.json，重编译后启动的新实例端口被占未监听；CLI 按 endpoint 连到旧实例，create 执行的是旧版「创建即切换」语义。而 T1-T5 exit 2 全过是因为 switch/close 拦截与缺 -P 校验都在 **CLI 进程本地**（不连服务端），恰好掩盖了「服务端是旧版」。修法：重编译后 `Get-Process PrismProxy` 核对 StartTime 与 exe LastWriteTime（不一致即旧实例），或直接 taskkill 全部再启动唯一实例再测。铁律：①exit code 通过 ≠ 服务端语义正确——先分清每个测试点是本地拦截还是打到服务端；②涉及「重建后重测」的场景，先盘点常驻进程新旧再动测；③config\ctl-endpoint.json 由最后写入的实例持有，多实例并存时它指向的不一定是你以为的那个。
