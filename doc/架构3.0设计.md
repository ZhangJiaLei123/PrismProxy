# PrismProxy 架构 3.0 设计：一后台 · 多 UI

> 状态：**设计待评审**（2026-09-18 写就，同日完成方案审计：3 项 P1 / 6 项 P2 / 11 项 P3 修订已回写本文，审计记录见 §15）。本文只定义架构与契约，不含实现排期；实施波次见 §13，落地后在 [开发进度.md](./开发进度.md) 记录。
> 相关文档：[方案.md](./方案.md)（2.x 总设计）、[CLI实时推送设计.md](./CLI实时推送设计.md)（ctlapi/SSE 基础）、[项目配置设计.md](./项目配置设计.md)（多项目隔离 M9/M11）。

## 1. 背景与问题

2.x 架构中，同一个 `PrismProxy.exe` 扮演三种角色：

| 启动方式 | 角色 |
|---|---|
| 双击 / 无参 | Wails GUI：窗口进程 = 业务后端（代理引擎、SQLite、规则、AI），ctlapi 只是"旁路控制面" |
| `-headless` | 无窗后端（调试/冒烟用），能力与 GUI 对齐但定位是"临时模式" |
| `cli ...` | 一次性命令行客户端，读 `config/ctl-endpoint.json` 连运行中的实例 |

由此产生的核心矛盾：**业务生命周期与一个 GUI 窗口进程强绑定**。

1. AI 通过 CLI 操作项目时，人要"看着数据"，只能去动那个唯一窗口——而那个窗口可能正是 AI 经 `ui:*` 指令驱动的窗口，人与 AI 在同一个 UI 上互相干扰。
2. 无法开第二个窗口（再双击 exe 要么重复启动后端抢代理端口/系统代理，要么没有意义）。
3. 后端只有**一个全局 currentProject**，想看另一个项目的历史数据，只能 `project switch` 把抓包目标一起切走。
4. headless 是"二等公民"：关 GUI 即停后端，无法作为长期常驻的数据采集服务。

## 2. 3.0 目标与拍板决策

**目标：一个常驻后台 + 多个可重复打开的 UI 客户端。** exe 只是 GUI 壳，可重复打开多个；每个 GUI 连接本机后台，选择观察/控制身份与要查看的项目。AI 继续走 CLI 操作，人工同时用 GUI 只读观测，互不干扰。

### 2.1 关键决策（2026-09-18 拍板；D5 追加于 2026-09-21）

| # | 决策点 | 结论 |
|---|---|---|
| D1 | exe 默认形态 | **智能一体**：双击 exe 时，后台不在则先拉起后台再开 GUI；后台已在则只开 GUI。可重复双击开多个 GUI 窗口 |
| D2 | GUI 权限 | **连接时选择「观察模式（只读）」或「控制模式」；控制模式全实例唯一，被占用时只能选观察模式**。第一个连接的 GUI 可选控制 |
| D3 | 项目模型 | **GUI 旁路只读任意库**：抓包仍只跟随后台唯一 currentProject；GUI 可额外旁路挂载任意项目做**只读**查看（实时列表/详情/复盘），不影响 CLI 的当前项目 |
| D4 | 多后台 | **只支持单后台**：不做注册中心/多实例发现，固定一个本机后台。端口冲突时直接报错引导，不做实例枚举 |
| D5 | 后台退出入口 | **serve 内置系统托盘（必做，非可选）**：后台被 AI/脚本以 detached 方式拉起后，用户必须有不依赖命令行的图形化入口——托盘提供「打开 GUI（连接后台当前项目）」与「彻底退出」（完整清理后退出进程，§4.4） |

### 2.2 非目标（3.0 明确不做）

- 不做后台多项目**同时抓包**（不引入多写库/多引擎会话；后台仍是单 currentProject）。
- 不做局域网/远程后台、多机管理、注册中心（仅 127.0.0.1 回环）。
- 不做浏览器 Web 多用户账号体系；身份仅限"本机连接级"。
- 不重写代理引擎 / MITM / SQLite / 规则引擎——全部复用。
- 不更换桌面框架（仍 Wails v2），3.0 是进程拓扑与通信层重构，不是重写。

## 3. 目标架构总览

```
┌─────────────────────────────── 本机用户会话 ───────────────────────────────┐
│                                                                            │
│   GUI#1 (PrismProxy.exe)   GUI#2 (PrismProxy.exe)   GUI#3  ... 可重复打开  │
│   控制模式（唯一）           观察模式（只读）          观察模式（只读）        │
│   挂载: current + 旁路A      挂载: 旁路项目B          挂载: current          │
│        │                        │                        │                 │
│        └────────────┬───────────┴───────────────┬────────┘                 │
│                     │  HTTP + Bearer token       │                          │
│                     │  数据: REST   实时: SSE     │                          │
│              ┌──────▼───────────────────────────▼──────┐                   │
│              │   PrismProxy 后台（serve，常驻进程）      │                   │
│              │   ctlapi（唯一对外业务面）  ◄──── CLI 子命令（AI/脚本）       │
│              │   ┌──────────────────────────────────┐  │                   │
│              │   │ App 服务层（与 2.x 同一套内核）    │  │                   │
│              │   │ 代理引擎 · MITM · 规则 · 代理池     │  │                   │
│              │   │ 活动项目写库(1) + 只读旁路库池(N)   │  │                   │
│              │   └──────────────────────────────────┘  │                   │
│              └──────────────────┬───────────────────────┘                   │
│                                 ▼                                           │
│                    设备/模拟器流量（9090/9091）                              │
└────────────────────────────────────────────────────────────────────────────┘
```

**不变**：代理引擎、CA、系统代理接管、ADB、规则、SQLite schema、多项目目录布局。
**变**：业务后端从"GUI 窗口进程"剥离为独立常驻进程；GUI 全部经 ctlapi HTTP/SSE 通信；新增连接身份、控制租约、旁路只读库会话三类机制。

## 4. 进程模型与启动流程

### 4.1 三种运行形态（同一 exe 子命令/开关）

| 形态 | 命令 | 说明 |
|---|---|---|
| 后台 | `PrismProxy.exe serve`（`--addr`/`--no-mitm` 沿用） | 常驻业务后端：代理 + ctlapi + 写库；**无窗口**。由 2.x `-headless` 正名演进 |
| GUI | `PrismProxy.exe`（无参，默认） | 只负责开窗口并连接后台；**自身不跑代理、不写库** |
| CLI | `PrismProxy.exe cli ...` | 同 2.x，一次性命令行客户端 |

> 兼容：3.0 保留 `-headless` 作为 `serve` 的隐藏别名，旧脚本不立即失效（后续大版本再移除）。

### 4.2 智能一体启动（D1）

无参启动（双击 exe）时的决策序列：

```
1. 读 config/ctl-endpoint.json（GUI 唯一允许读取的配置文件，例外条款见 §4.5），GET /api/v1/health（短超时 ~300ms）
   ├─ 通 → 后台已在 → 直接进入「连接」步骤 3
   └─ 不通/无文件 → 后台未运行
2. 拉起后台：以隐藏控制台方式启动 "PrismProxy.exe serve"（detached，独立进程组）
   ├─ 轮询 /api/v1/health（指数退避，总预算 ~10s）
   ├─ 后台就绪 → 继续步骤 3
   └─ 超时/失败 → GUI 显示致命错误页（日志路径、手动 serve 命令、重试按钮）
3. GUI 打开连接栏：展示后台版本/当前项目，选择身份（观察/控制）与挂载项目
```

要点：

- GUI 与后台是**两个进程**：关所有 GUI 窗口，后台继续常驻（AI/CLI 与采集不中断）。
- 后台是"智能拉起"而非"随第一个 GUI 生死"；停止后台只通过显式入口：托盘（§4.4）或 `cli serve stop`。
- 重复双击 exe = 重复步骤 1，因后台已在，故每次只新增一个 GUI 进程/窗口。
- 被 GUI 拉起的后台与手动 `serve` 无差别；GUI 不持有后台进程句柄做"退出联动"。

### 4.3 单实例保证（D4）

- ctlapi 仍固定绑 `127.0.0.1:9595`。第二次 `serve` 因端口占用**直接失败**并输出明确指引（"后台已在运行，直接打开 GUI 即可；如确认残留，先 cli serve stop"），不做端口自增、不做实例列表。
- Windows 侧增加一个命名互斥量（如 `Global\PrismProxyServe`，限当前用户会话用 `Local\` 前缀即可）作为端口竞争之外的第二道保险，错误文案统一。
- `config/ctl-endpoint.json` 继续作为发现文件（addr+token）；token 仍每次后台启动随机重生成，所有 GUI/CLI 在后台重启后重读（沿用 2.x 契约）。

### 4.4 后台的可感知性与生命周期

- **动机（D5，2026-09-21 拍板）**：后台既被 GUI 智能拉起，也可能被 AI/脚本以 detached 方式直接启动——后者无窗口、无人守着终端，若只有 `cli serve stop` 一个停止入口，普通用户将**无法退出后台**；用任务管理器强杀又会跳过清理，留下系统代理/ADB 接管残留。因此 serve 进程**必须内置系统托盘**（由后台进程自身创建，Go 托盘库如 fyne.io/systray——Wails v2 无原生托盘 API；非 WebView），随 serve 形态同波落地（W1），不再是可选件。
  - 托盘菜单：①状态行（tooltip + 菜单首行禁用项：当前项目、代理运行状态、在线 GUI 数）；②**打开 GUI**——启动无参 exe，经智能探活（§4.2）连接本后台，即可查看/操作当前项目；③**退出后台**——带确认（提示"有 N 个 GUI 连接中"），执行与 `cli serve stop` 完全相同的清理管线（还原系统代理、清 ADB 设备代理、刷盘关库、删 endpoint 文件）后退出进程。
  - 托盘是后台进程的一部分，保证"所有 GUI 关闭后仍可感知并退出后台"；serve 是交互用户会话内的普通进程（非 Windows 服务），detached 启动也能正常显示托盘图标。
  - 过渡期语义：W1–W4 期间无参 exe 仍是 2.x 同进程形态，「打开 GUI」菜单项置灰（避免引导旧 GUI 与 serve 双后端并存写同一库）；W6 起启用。
  - `cli serve status|stop` 保留为脚本化兜底入口；serve 内部仍需一个隐藏窗口承接关机/注销消息（watchSessionEnd，见下条）。
- 后台退出清理沿用 2.x headless：还原系统代理、清 ADB 设备代理、刷盘关库、删 endpoint 文件；系统关机/注销的隐藏窗口消息处理（session_windows.go，现状仅 GUI 进程 Startup 注册）整体迁到后台进程（随 W1 落地，§13）。
- 崩溃自愈（sysproxy SelfHeal）在后台启动时执行（同 2.x）。

### 4.5 与便携模式/构建的关系

- **配置目录归属后台**：`config/`（settings.json、ca/、projects/、ctl-endpoint.json）只由 serve 进程读写，位置仍为 **serve 进程 exe 同级 config/**（便携模式不变）。
- GUI 进程不写 config，不读 CA/DB/settings；业务数据与配置一律经 API 获得。**唯一例外（只读）**：GUI 壳读 `config/ctl-endpoint.json` 获取 addr+token 以探活/连接后台（§4.2）。本地文件选择对话框只经内存中转，不落 config（见 §9.3）。
- 单 exe 交付不变：serve / GUI / cli 同一体积的单文件；`go:embed frontend/dist` 同时用于 ctlapi 静态托管（review.html）与 GUI 壳（Wails 资产）。Wails 生产构建标签约束（裸 `go build` 弹窗）维持现状。

## 5. 连接、身份与控制租约

### 5.1 客户端身份

每个连接到 ctlapi 的客户端必须有身份。两类：

- **CLI**：本机可信命令行，默认全权（沿用 2.x，不被租约阻塞，见 §5.5）。
- **GUI 连接**：需先注册获得 `clientId`，声明角色 `observe`（观察）或 `control`（控制）。

`clientId` 由 GUI 启动时生成（随机 32B hex），在后续请求头 `X-Prism-Client` 与 SSE query 中携带，用于租约占用、在线列表与事件定向。

### 5.2 控制租约（D2）

- 后台内存维护**唯一控制租约** `controlLease { clientId, clientName, acquiredAt, lastSeen }`。
- GUI 连接时：
  - 请求控制 → 租约空闲则获得（200 + 租约信息）；已被占用则 409，返回占用者名/获取时间，前端强制只能进观察模式。
  - 请求观察 → 永远成功（观察连接数量有上限，沿用 SSE 订阅上限思路，默认 16）。
- 租约**不跨后台重启保留**（内存态；后台重启后所有 GUI 重新竞争，符合"第一个打开的可选控制"）。
- 续约与释放：
  - 持有控制的 GUI 每 10s 心跳 `POST /api/v1/session/heartbeat`；后台 30s 未收到心跳 → 判定失活，释放租约并广播 `lease` 事件。
  - GUI 正常关闭/主动放弃 → `POST /api/v1/session/release`；进程崩溃靠心跳超时兜底。
  - 观察模式 GUI 可在租约空闲时**升级**为控制（同一连接 `POST /api/v1/session/acquire-control`），无需重开窗口；控制方也可主动降级为观察。
- 后台重启（instanceId 变化）→ 所有 GUI 收到 SSE 断连/新 open 帧，重新走注册与租约流程。

### 5.3 权限矩阵

| 操作 | CLI | GUI 控制 | GUI 观察 |
|---|---|---|---|
| 看实时流/详情/body/复盘/标签数据（任意项目） | ✅ | ✅ | ✅ |
| SSE 订阅 flows/status/proxypool/project/lease | ✅ | ✅ | ✅ |
| 启停代理、系统代理接管、reset-bypass、装 CA | ✅ | ✅ | ❌ |
| project switch/create/rename/delete/close | ✅ | ✅ | ❌ |
| 改规则/域名组/设置/AI 配置/代理池 | ✅ | ✅ | ❌ |
| clear flows、pin、quick ignore、compose 重发 | ✅ | ✅ | ❌ |
| 打标（写 review_tags/intents）、忽略名单增删 | ✅ | ✅ | ❌（观察模式复盘页为纯查看） |
| AI chat（外发请求） | ✅ | ✅ | ❌ |
| 挂载/卸载旁路只读项目（/session/mounts，仅影响本连接会话） | ✅ | ✅ | ✅ |
| serve stop（停止后台） | ✅ | ❌（停止入口在托盘，§4.4） | ❌ |

观察模式 UI：所有写入口置灰/隐藏并标注"观察模式"，但页面数据完整可见。后端**必须独立强制**（不能只靠前端置灰）：业务写路由在解析身份后，对 observe 角色统一返回 `403 observe-only`。注意定位（P2-4）：observe-only 403 是**权限策略（防呆、防误操作）而非安全边界**——观察 GUI 同样持有 token，本机恶意进程可自行声明 cli 角色绕过；本机威胁边界仍由回环绑定 + 0600 endpoint 文件承担（§5.4/§11）。

### 5.4 鉴权链路（token 之外加一层角色）

- 所有 `/api/v1/**` 仍需 Bearer token（2.x 不变）。
- 写路由额外要求角色 ∈ {cli, control}。CLI 如何被识别为 cli：CLI 侧固定发 `X-Prism-Client-Role: cli` 头 + endpoint 文件内 token。token 本身即本机能力凭证，2.x 已等同全权，故不为 CLI 引入新密钥；该角色头仅用于后台在在线列表/日志中区分调用方，**安全边界仍由 0600 endpoint 文件 + 回环绑定 + ACL 承担**（与 2.x 威胁模型一致）。
- GUI 未注册 clientId 的写请求一律 401/403。
- 会话自身操作（clientId 注册、心跳、租约申请/释放/升级、挂载/卸载）虽是 POST 但**不属于业务写**，对所有 GUI 角色开放；`/serve/stop` 仅接受 cli 角色（GUI 的停止入口是托盘，§4.4/§8.1，P2-7）。

### 5.5 与 CLI（AI）并发的冲突语义

- CLI 写操作**不申请、不等待控制租约**（D2 只约束 GUI 之间；AI 经 CLI 是首要自动化入口，不能被一个 GUI 窗口挡住）。
- 因此"GUI 控制 + CLI 写"可能并发修改同一状态。3.0 不做强分布式锁，沿用并补强 2.x 已有的**乐观并发**：
  - settings/规则保存继续带 `rulesProject` 令牌（2.x 已存在），过期拒绝（409）。
  - project 切换继续用 projGen 代际（2.x 已存在）。
  - 控制方 GUI 在后台发生"非自身发起"的写变更时，经 SSE `status`/`project`/新增 `config-changed` 事件收到通知，自动刷新视图，并在设置页提示"配置已被 CLI/其他端修改，当前视图已重载"。
- 这是刻意取舍：AI 自动化可用性 > GUI 写互斥；GUI 观察模式才是"AI 干活时人工介入"的推荐姿态（D2/D3 的本意）。

## 6. 项目模型：单活动项目 + N 个旁路只读挂载（D3）

### 6.1 概念

- **活动项目（active）**：后台唯一 currentProject，2.x 语义完全不变——抓包落 `projects/<id>/prism.db`、规则引擎/解密/域名组都对它生效、CLI `project switch` 切它。
- **旁路挂载（bypass mount）**：GUI 可附加打开任意其他项目（甚至活动项目自身）的库做**只读**查看。挂载是**会话级**的：只读 DB 句柄以 projectId 为 key 全局共享（同项目多 GUI 复用一个连接，§6.3），按 clientId 记引用计数；某 GUI 断开或卸载只减引用，归零且空闲超时才真正关闭句柄。旁路项目**不影响代理引擎、不切规则、不落新流量**。

### 6.2 数据可见性

| 视图 | 挂载=活动项目 | 挂载=旁路项目 |
|---|---|---|
| 实时流（SSE flows / 内存 store） | 有，实时 | **无实时**（旁路项目不是抓包目标，后台不会为它推流） |
| 历史流列表/详情/body | 走内存 store + 活动库 | 走旁路只读库（persist 历史查询） |
| 复盘（标签/直方图/忽略过滤/AI 结果回看） | 同 2.x | 同口径，数据源换旁路库 |
| 规则/域名组展示 | 活动配置（内存） | 只读展示该项目 project.json（不落引擎） |
| 写操作 | 按 §5.3 角色 | 一律禁止（即使是控制 GUI，旁路项目也只读） |

旁路项目 UI 上明确标识「只读历史 · 非实时」，并提供"切到活动项目看实时"的入口（仅控制 GUI 可执行 switch；观察 GUI 点了提示无权限）。

### 6.3 后端实现要点（复用现成基础）

- 只读打开直接用 `persist.OpenReadOnly(dbPath)`（已存在：`mode=ro` + `query_only` 双保险、不建文件、不 migrate）。WAL 模式下多个只读连接与一个写连接可安全共存。
- 新增**只读库会话池**（internal/app，建议 `mounts.go`）：
  - key = projectId（同机同项目共享一个只读句柄，避免每个 GUI 各开一个）；value 记 `*persist.Writer`（只读）+ refCount + lastAccess。引用以「GUI 连接的挂载会话」为单位：显式挂载 +1、显式卸载 -1（P1-3 统一口径）。
  - **失联释放（P1-3）**：GUI 的 SSE 连接断开视为该连接可能已死。断开后启动宽限期（默认 60s，GUI 重连即撤销），宽限期内未恢复 → 后台对该 clientId 名下全部挂载 -1 并广播 clients 变化；引用归零且空闲超时（如 5 分钟）自动关闭句柄。防强杀 GUI 后句柄悬挂导致项目删不掉（M11 同款复发）。
  - 空闲超时自动关闭释放文件句柄（Windows 下项目删除/切换时句柄占用敏感，参考 M11 enterNoProject 先释句柄再删目录的教训）。
  - 活动库本身不进旁路池，避免与录制/归档写句柄混用；旁路挂载活动项目时返回"实时视图"而非另开只读句柄（或内部特判）。
- 查询入口在现有复盘/历史查询服务方法上增加一个**数据源解析参数** `mount=<projectId|""> `：
  - 空 = 当前 2.x 行为（活动：内存实时 + 活动库归档）。
  - 非空 = 校验项目存在 → 取/建只读句柄 → 走与活动库完全相同的只读查询函数（ReviewFlowList/Histogram/FlowDetail/Body/TagsOverview 等），保证两路口径一致（同一 buildFlowQuery、同一忽略名单语义）。
- 旁路项目的忽略名单、标签是**该项目库内数据**，只读；不在旁路库上执行任何写（打标/加忽略对旁路项目返回 403）。
- 被旁路的项目正被 `project delete` 删除时，必须走**完整并发序列**（由 projMu 串行化，复刻 M11「先释句柄再删目录」，P2-6）：
  1. projMu 内：挂载池标记该 projectId 失效（新查询/新挂载一律 404）；
  2. 广播 `project:deleted`（SSE project 频道），前端回到选择页；等待在飞只读查询返回（只读查询毫秒级，短暂等待即可）；
  3. 解锁 projMu 后关闭该项目的只读句柄（关句柄动作不持 projMu，避免与 mount 查询互锁；失效标记保证不会有新查询再拿到句柄）；
  4. 引用归零、句柄全关后删除项目目录；若句柄仍被占用（异常）→ 报错保留目录并日志告警，绝不半删。

### 6.4 API 形态（mount 参数）

统一用 query 参数 `mount=<id>`，不带即活动：

```
GET /api/v1/flows?mount=<id>                 # 旁路：从该库读最近 N 条历史（非实时）
GET /api/v1/flows/{id}?mount=<id>            # 单流详情
GET /api/v1/flows/{id}/body?which=&mount=<id>
GET /api/v1/tags?mount=<id>
GET /api/v1/tags/{id}/flows?...&mount=<id>
GET /api/v1/tags/{id}/histogram?...&mount=<id>
GET /api/v1/projects/<id>/snapshot           # 旁路项目元信息 + project.json 只读视图（规则/域名组清单）
POST /api/v1/session/mounts  {projectId}     # 挂载（建只读句柄，返回可查范围/有无 prism.db）
DELETE /api/v1/session/mounts/{projectId}    # 释放（引用计数 -1）
GET  /api/v1/session/mounts                  # 本连接已挂载列表
```

- mount 非法（项目不存在/库文件不存在）→ 404 或返回"空库可挂载但无数据"标志，由前端显示空态（未开启持久化的项目没有 prism.db，属正常）。
- SSE flows 不按 mount 分流：实时流恒属于活动项目。旁路挂载不需要也不获得实时频道。

## 7. 实时事件（SSE）扩展

沿用 `/api/v1/events`（SSE、15s 心跳、open 帧带 instanceId、先订阅后快照、背压 reset）。3.0 增量：

| 频道/事件 | 现状 | 3.0 |
|---|---|---|
| `flows` | upsert/evict | 不变（恒活动项目） |
| `status` | 代理/系统代理 | 不变 |
| `proxypool` | 已有 | 不变 |
| `project` | 2.x 是 Wails 事件 `project:changed`，未走 SSE | **新增** SSE 频道：project-switched / project-created / project-renamed / project-deleted / project-closed，载荷含 current 与变更项目 |
| `lease` | 无 | **新增**：控制租约 acquired/released/lost，载荷含 clientName（观察 GUI 据此显示"当前控制者"并可在空闲时申请升级） |
| `clients` | 无 | **新增（可选）**：在线 GUI 连接/角色列表增删（连接栏与托盘展示用） |
| `config-changed` | 无 | **新增（可选）**：非本客户端发起的 settings/规则/AI 配置写变更，提示控制 GUI 重载 |
| `index-import-progress` | 仅 Wails 事件 | 域名组批量导入进度改/补 SSE（HTTP 客户端可见） |

事件白名单 `allowedChannels` 扩充；所有新事件继续走 Hub fan-out，遵守不过滤关键帧（类比 evict 必达）、订阅上限、query token 仅 /events 接受的既有铁律。

**客户端订阅契约**（P3-10，实现时固化进 src/client/eventClient）：① **先订阅后快照**——收到 open 帧确认订阅建立后才拉 REST 快照，消除"快照后、订阅前"丢事件窗口；② open 帧内 instanceId 与本地不同 = 后台重启过 → 全量重订阅 + 重快照 + 按本地会话重挂载（§9.2）；③ 收到 reset 按背压语义重拉快照；④ SSE 重连期间 UI 进入失联遮罩，不展示可能过期的实时数据。

## 8. ctlapi 能力差集与补面清单

2.x 主窗大量操作走 Wails 绑定 + Wails 事件，GUI 全 HTTP 化后必须把"仅 Wails 可用"的能力补到 ctlapi。基于绑定清单比对，差集分四类：

### 8.1 需新增的 HTTP 端点（真能力缺失）

| 能力 | 现状 | 3.0 端点/方案 |
|---|---|---|
| AI 模型列表下拉 | Wails `FetchAIModels(cfg)` | `POST /api/v1/ai/models`（body 为待试配置，服务端 ListModels，1MB 限读） |
| 连接/租约/挂载 | 无 | §5/§6 的 `/session/**` |
| 项目旁路元信息 | 无 | `GET /projects/<id>/snapshot` |
| 健康探针 | 无专门端点（status 偏重） | `GET /api/v1/health` → `{ok,version,instanceId,currentProject,proxyRunning}`，**免 token**（仅回环、仅非敏感健康字段，供智能启动探活） |
| 后台停止 | 无 | `POST /api/v1/serve/stop`（**仅 cli 角色**，GUI 角色调用返回 403——GUI 的停止入口只有托盘，§4.4/§5.4；等同托盘退出，执行清理后退出进程） |
| 域名组文件导入进度 | Wails 事件 | 复用 §7 SSE；端点已有 `/domains/import` |

其余写/读能力（规则、设置、代理生命周期、CA、ADB、证书注入、域名组 CRUD、compose、tags、AI config/test/chat、代理池全套）ctlapi **均已存在**，只是部分主窗在用 Wails 同名绑定。3.0 让 GUI 统一改走 HTTP 即可，无需重复造业务逻辑。

### 8.2 客户端本地化（不应进后端，GUI 自己做）

| 能力 | 2.x | 3.0 |
|---|---|---|
| 文件/目录选择对话框（PickAdbPath、导入选文件、导出落盘） | Wails 原生 OpenFileDialog | **GUI 进程本地调用 Wails 对话框**，拿到路径/内容后再以"路径或内容"调 HTTP（导入已有 src=本地路径 的 `/rules/import`、`/domains/import`；导出 ctlapi 返回 JSON 原文，由 GUI 本地写文件） |
| 下载/保存响应体、cURL 到文件 | 前端 + Wails | GUI 本地 Blob 下载 / 写文件（Wails dialog），数据来自 HTTP |
| 窗口最小化/恢复（WindowUnminimise） | Wails runtime | GUI 本地行为，保留 |

结论：GUI 壳**保留 Wails runtime 仅用于**：资产承载、窗口控制、原生文件对话框、（托盘在后台不在 GUI）。所有**业务数据与业务动作**走 HTTP。

### 8.3 被取代的 Wails 事件桥（改为 SSE/HTTP）

- `flow:upsert/flow:evict` → SSE flows（2.x 已同源同批次）。
- `proxy:ready/proxy:start-error` → SSE status（seed + 发布点已齐备）。
- `project:changed` → SSE project（§7）。
- `ai:chat`（Wails 事件桥 + AIChatStart/Stop 绑定）→ 直接 `POST /api/v1/ai/chat` SSE。review 页的 `HttpApi` 已实现这条链路，主窗 AI 面板与其共用同一套 HTTP/SSE 客户端代码即可（统一 review/api 与主窗数据层，见 §9）。
- `ui:open-settings` / `ui:clear`：2.x 是 CLI→GUI 反向驱动单窗口。3.0 语义变化——**不再有"那个唯一窗口"**。`ui clear` 作为数据操作保留（清活动 store，本来就是数据级）；"打开设置面板"这类**纯界面动作不再跨进程指定某窗口**：CLI 若要提示人工，改为可选地广播一个 SSE `ui-notice`（建议性），各 GUI 自行决定是否弹出（控制者响应、观察者可忽略）。`ui settings` 在无 GUI 时返回 `{ui:false}` 的 2.x 语义相应弱化。

### 8.4 工具/版本类

- `GetVersion/CheckUpdate/GetLocalAddrs/FindFreePort/ListSystemProcesses`：
  - version/health 进 HTTP（§8.1）。
  - 本机地址、空闲端口探测、系统进程枚举：这些是"后端所在机器"的信息，补只读 HTTP 端点（GET `/meta/local-addrs`、`/meta/find-free-port?ip=&start=`、`/processes` 已有）。GUI 控制模式设置页可用；观察模式可读但不可改。
  - 更新检查：后台或 GUI 任一侧发起均可，放后台 GET `/meta/check-update` 更一致（网络出口统一）。

### 8.5 Service 接口维护铁律延续

新增 Service 接口方法必须同步三处（2.x 铁律）：`ctl_bridge.go` 适配、`ctlapi_test.go` fakeService 桩（`var _ Service` 编译断言）、以及如仍有 Wails 绑定则 wailsjs 三文件。3.0 目标是**逐步收薄 Wails 绑定**到只剩本地能力（§8.2），新增业务方法一律只加 ctlapi、不再加 Wails 业务绑定。

## 9. 前端架构改造

### 9.1 通信层统一

- 现状：主窗数据层 = Wails 绑定（`wailsjs/go/app/App`）+ Wails 事件；复盘页数据层 = `review/api`（Demo/Http/Wails 三实现 + createApi 工厂）。
- 3.0：**新建统一客户端 `src/client/`**（建议直接把 review/api 的 HttpApi/SSE 经验提升为主层）：
  - `apiClient`：baseURL + token + clientId/角色注入；统一错误映射（401 未授权 / 403 observe-only / 409 租约占用或规则令牌过期 / 404 挂载不存在 / 503 订阅满）。
  - `eventClient`：SSE 封装（open/instanceId 变化检测、重连重拉快照、reset 背压处理、channels 订阅）。
  - 主窗 stores（flows、useProjects、usePoolStatusEvent、useAiSession 等）从 Wails EventsOn/绑定切换到 client。
  - 删除/停用主窗对 `wailsjs/go/app/App` 业务方法的依赖；wailsjs 仅保留 §8.2 本地能力（dialog/window）。
  - **CORS（P1-2，GUI 壳 HTTP 化的前置依赖）**：GUI 页面 origin 为 `http://wails.localhost`（Wails WebView2），对 `http://127.0.0.1:9595` 的 fetch/流式 SSE 均为跨域，而 ctlapi 现状**无任何 CORS 处理**（已核验 server.go 无 cors 中间件），GUI 壳的第一个请求就会被浏览器拦截。方案：ctlapi 增加回环限定 CORS 中间件——`Access-Control-Allow-Origin` 仅放行 Wails origin（`http://wails.localhost`），放行 `Authorization`/`Content-Type`/`X-Prism-Client`/`X-Prism-Client-Role` 头与 GET/POST/PUT/DELETE/OPTIONS（含流式响应）。**方法/头清单必须覆盖 ctlapi 既有全部动词**（已核验：代理池与 AI 配置更新用 PUT、标签与代理池账号删除用 DELETE、3.0 卸载挂载用 DELETE；漏放 `Content-Type` 则 POST/PUT JSON 预检直接失败），漏放行会让 GUI 壳对应请求被浏览器拦截。CORS 只解决浏览器 origin 校验，不改变「仅 127.0.0.1 绑定 + token」的网络边界（§11）；实现随 W1 的 /health 一起落地。
- PascalCase（FlowMeta 无 json tag）与小驼峰（settings/status）的字段口径差异维持现状，客户端类型层不动既有 DTO 定义。

### 9.2 应用骨架变化

- 启动顺序：资产加载 → 连接栏（ConnectBar/连接页）→ 注册身份/租约/选挂载 → 进入主界面。
- 新增状态：
  - `session { connected, instanceId, role: observe|control, clientId, leaseHolder }`
  - `mounts { active: 当前实时项目, bypass: [旁路项目...], currentViewProjectId }`
  - 顶部连接状态：后台版本、连接点（127.0.0.1:9595）、角色徽标（观察/控制）、当前挂载项目、租约占用者；断开时进入"重连/后台失联"遮罩。
- 观察模式：全局写控制（按钮禁用 + 只读提示）由一个权限判定收口（`canWrite = role==='control' && viewProject===active`），避免散落判断。
- 项目选择器：活动项目（标"实时"）+ 任意旁路项目（标"只读历史"）。切换旁路项目时，实时流页改为"历史流（非实时）"视图（走 mount 查询 + 轮询/手动刷新，不接 flows SSE）。
- 无项目态（M11 欢迎页）保留：活动项目为空时，控制 GUI 可创建/打开项目；观察 GUI 只能旁路选择已有项目或看空态。
- 连接栏支持"放弃控制/申请控制"（租约空闲时申请，被占时显示占用者）。
- **重连重放（P3-15）**：失联遮罩期间保留本地会话意图（角色 + 挂载列表）；重连成功后自动重新注册、申请租约、重挂载（/session/mounts 对已挂载项目幂等返回现状而非报错），失败项提示用户手动处理。
- **切换残影防护（P3-20）**：切换 viewProject 时先整体清空旧项目数据（flows/详情/body/复盘视图）再载入新数据源；旁路视图的 flows 列表仅由 mount 查询填充，绝不混入活动项目内存 store 数据，防止跨项目数据残影误导。

### 9.3 本地能力保留点（仍 import wailsjs/runtime 与 dialog）

- 读取 `config/ctl-endpoint.json`（只读；GUI 壳启动/重连时获取 addr+token，是 GUI 对 config 的唯一例外，§4.5）。
- 打开/保存文件对话框、ADB 路径选择、规则/域名组导入导出的本地文件落地。
- 窗口最小化/恢复等窗口动作。
- 其余全部 `EventsOn/EventsEmit` 业务事件移除（mocks 可保留用于纯前端演示，但演示数据不应再被当作一种"传输实现"进主链路）。

### 9.4 多窗口

- 多窗口 = 多进程，各自独立 Pinia/IndexedDB（AI 会话历史等本地态天然隔离，互不影响）。无需前端跨窗口同步——一切以后台 SSE 为准，天然最终一致。
- 同一台机重复双击只是再开一个 WebView2 进程，资源可接受；观察连接上限在后端兜底（§5.2）。

### 9.5 复盘页 / AI 面板

- 复盘页 createApi 的 token 探测改为从统一 session 取（GUI 内嵌页不再依赖 URL `?token=`）。为兼容 2.x 的 review.html 浏览器直开方式保留 query token，且**该形态在 3.0 中定义为只读观察**（P2-5）：无 GUI session/clientId，可读数据与订阅 SSE，业务写一律被拒——query-token 连接无 clientId，按 §5.4 未注册口径返回 401/403（§5.3 observe-only 语义同样覆盖该连接；写操作请走 CLI）。
- AI 面板主窗与复盘共用 `/ai/chat` SSE 实现；观察模式禁用发起（外发红线：仅控制/CLI 可发起 AI）。AI 历史/导出/三模式持久化等前端能力不变。
- 旁路项目中的复盘 AI：数据可见，但"AI 分析"按钮在旁路 + 观察下禁用；是否允许控制 GUI 对旁路项目发起只读 AI 分析（不外发数据的前提下没有意义——AI 必然外发），3.0 规定**旁路项目不发起 AI**（避免把非活动库数据外发的语义混乱）。

## 10. 后端结构改造（Go）

### 10.1 模式装配

- 新增明确的 serve 装配（替代 headless 的"调试"定位）：`app.RunServe(addr,noMITM,assets, opts)` 负责 SelfHeal → 启动代理 → startCtlAPI → 托盘（必做，D5）→ 信号/会话消息等待 → 清理。本质是把现有 RunHeadless 正规化并加托盘/停止端点。
- GUI 装配（main 包 Wails）只做：EnsureWebView2 → NewApp **不再实例化业务内核**（不再 NewApp 代理/DB）→ Wails 窗口承载前端，前端经 HTTP 连后台。即 GUI 进程的 `internal/app` 依赖收缩到几乎为零（可能只留 dialog/version/webview2 自检）。
- `main.go` 分派：`serve`/`-headless`(别名) → RunServe；`cli` → RunCLI；无参 → 启动 Wails GUI 壳。

### 10.2 新增包/文件（建议）

- `internal/ctlapi/session.go`：clientId 注册、控制租约（获取/释放/心跳/升级/失活扫描）、在线列表、角色鉴权中间件、`/session/**` 与 `/serve/stop`、`/health`。
- `internal/app/mounts.go`：旁路只读库会话池（OpenReadOnly 复用 + 引用计数 + 空闲关闭 + 删除联动）。
- `internal/ctlapi` 各 handler 增加 `mount` 解析与只读数据源路由；写 handler 接角色守卫。
- `internal/app/tray_*.go`（必做，随 W1）：系统托盘（D5；跨平台拆 other/windows，同 acl/session 范式）。

### 10.3 锁与代际（沿用 2.x 红线）

- 新增租约锁、挂载池锁独立，**不进入** `projMu → a.mu/a.pmu` 既有锁序；挂载池建/关只读句柄不得在持 a.mu/a.pmu 时做（避免与 M11 删库释句柄路径互锁）。
- mount 查询为只读路径，禁止触发 store emit / persist 写（遵守 pmu 临界区不得 emit 的死锁红线）。
- project delete/switch 与挂载池关闭句柄的顺序：先在 projMu 段标记项目失效/摘挂载 → 解锁后关只读句柄，复刻"先释放句柄再删目录"。

### 10.4 兼容性

- 旧 `-headless` 脚本：保留别名。
- 旧"无参直接出 GUI 且同进程带后端"的用法消失——无参改为智能拉起独立 serve。需在 README/帮助显式说明（对单机用户体验无感，仍是双击即用）。
- ctlapi 既有路由签名尽量不改，只新增 mount/session 等参数与端点，保证旧 CLI（2.x）连 3.0 后台时读操作基本可用（写操作的角色头：未带 X-Prism-Client-Role 的 Bearer 请求，3.0 过渡期可凭 token 视为 cli 全权，避免 2.x CLI 与 3.0 后台互操作全断；建议保留一个版本周期）。

## 11. 安全模型（延续 + 增量）

- 维持：仅 127.0.0.1 绑定；token crypto/rand 32B、常量时间比较、每次后台启动重生成；endpoint 文件 0600 + icacls 限当前用户、退出即删；query token 仅 /events；CA 私钥 ACL；apiKey 不外泄（掩码视图）。
- 新增：
  - `/health` 免 token 但只回非敏感字段，且仍仅回环。
  - 写操作角色强制（observe-only 403），后端不信任前端置灰（定位为权限策略而非安全边界，见 §5.3）。
  - 回环限定 CORS 中间件：仅放行 Wails origin（`http://wails.localhost`）与既有方法/头（§9.1），不扩大网络可达面。
  - 旁路只读连接 `query_only`/`mode=ro` 双保险（现成），杜绝只读挂载误写。
  - clientId 只是路由/展示标识，不作为密钥；能力边界仍由 token + 回环 + 文件 ACL 保证。
  - AI 外发：观察模式与旁路项目禁止发起（隐私红线，同 §9.5）。

## 14. 风险与开放问题

1. **Wails GUI 壳能否几乎不带业务内核**：需确认 assets/window/dialog 之外，前端是否还有必须同步调用 Go 的残留（如 GetFlowRawText 复制原文、CA 页面在代理端口的托管）。迁移时以 §8 清单逐项核销；CA 下载页本就由代理端口提供，与 GUI 进程无关。
2. **detached 拉后台的窗口闪现/控制台属性**：Windows 用隐藏窗口 + 独立进程组启动，避免黑色控制台闪烁；日志改落 `logs/`（或 config/logs）而非 stdout（便携/双击场景无控制台）。日志路径需在 GUI 致命错误页可达。
3. **2.x GUI 与 3.0 后台 / 2.x CLI 与 3.0 后台的跨版本兼容窗口**：建议保留一个版本周期的"Bearer 即全权"与 -headless 别名，并在 health/version 暴露协议版本，前端据此提示升级。
4. **控制租约是否会让人工"想临时操作却拿不到控制"**：观察→控制升级是一键的（租约空闲即得）；AI 只用 CLI、不占 GUI 租约，故任何时候最多只有一个 GUI 持控，人工随时可在持控者关闭/失活后接管。若实测仍别扭，可再评估"控制多主 + 全乐观冲突"，但 3.0 先按 D2 单控制落地。
5. **旁路项目无实时是否满足"观测项目数据"**：D3 已明确旁路是只读历史；真正实时盯当前抓包仍看活动项目。若未来需要"多设备多项目同时实时采集"，那是 D4 之外的多后台/多会话架构，不在 3.0。
6. **托盘的第三方依赖与会话可见性**：Go 标准库无托盘 API，需引第三方库（如 fyne.io/systray），打破"标准库为主"惯例但仅限 serve 进程使用；托盘归属交互用户会话，RDP 断开/会话注销后图标不可见属预期（此时由关机/注销清理管线兜底）。
